## 安全点的确定性派生规则

门点本身位于建筑碰撞边缘，不能直接作为角色脚部的返回坐标。令 `P` 为表中的入口坐标，`Q` 为其所连接步道的外端，沿该条步道向外取 2.4 米，再把两个分量四舍五入到小数点后两位：

```text
exterior = round_2(P + 2.4 × (Q - P) / |Q - P|)
```

2.4 米是本项目为角色碰撞留出的游戏设计距离，并非门厅或台阶的实测尺寸。所有步道均长于 2.4 米，因此派生点仍落在各自的步道线段内（舍入误差在厘米量级）。

|---|---|---|---:|

出口 ID 是既有游戏平面上的标识。它们与真实门号的对应由建筑展示旋转后的沿边顺序确定，不表示现实中的南北侧。对独立 OSM 轮廓应用 203° 展示旋转后，主入口位于凹进门厅，6、5、4 号门沿画面右侧自下而上，1、2、3 号门沿左侧自下而上。复核人对七个旋转后门点与既有室内平面门点进行了匹配，最近距离均小于 2.2 个室内格，顺序一致；这是游戏平面对应关系，不是室内测绘精度。

## 已执行的检查与适用边界

2026-10-26 使用仓库 [geometry.js](../../public/apps/jlu-campus/geometry.js) 和完整南区 JSON 执行了以下只读检查：

1. 从压缩原始 XML 解析建筑 way、全部 `nd` 引用及七个入口的原始标签，核对 JSON 顶点与 POI。
2. 对每个门扫描共享该节点的原始 ways，确认表中的唯一相连步道及两端节点。
3. 按上式计算并舍入安全点；七点均位于校园边界内。
4. 七点分别通过 `createWorld(data).isWalkable(x, y, 0.65)` 和 `isWalkable(x, y, 1.5)`，共 14 个可行走结果均为 `true`。
5. 对全体建筑、水域的所有外环与内环逐段计算最短距离，并排除位于实体内部的点，得到表中 2.397–2.402 米间距。

这组检查确认数据来源、映射和静态碰撞余量。服务端的七门白名单、进入时选择对应室内出生点、退出时返回对应室外点及多人状态同步，仍由相应运行时代码和功能测试负责，不能仅凭本数据核验视为已通过。

OSM 快照未提供这些门的当前开放时间、临时封闭或门禁状态，也未提供本楼经过授权的真实室内平面。`entrance=yes` 和 `entrance=main` 不能推导“现时允许通行”。本项目的室内房间、商店和通行设计属于游戏场景；本文只证明室外七门节点及步道的公开数据依据。若要宣称真实通行状态或精确室内导航，需要另外取得并核验对应资料。
