# 吉林大学前卫校区像素校园技术方案

更新：2026-10-25。工程位置：`public/apps/jlu-campus/`；计划入口：`/apps/jlu-campus/plan.html`；游戏入口：`/apps/jlu-campus/index.html`。

## 目标与交付边界

在现有“丁康的工作空间”中建设完整校园漫游与真实多人联机，先使用站点托管与数据库，后续可迁至自有云。验收参照 `https://jluai.bitmiracle.cn/campus/`，包含完整场景、角色与遮挡、全校地图、地标交互、重点室内、动态环境、分组、消息和重连。不能用几栋楼的样板、地图图片、假的在线人数或同浏览器消息广播替代完整体验。

最近核验运行版本为v17，北区出生点可辨识性已通过真实UI复核；北区23栋未名建筑的精确资料补全单独暂停。真实地图漫游和联机已可使用，长期容量与视觉近似完全未验收。

本方案先固定范围、数据和技术约束，再实施功能；`plan.json`保存任务状态，`验收矩阵.md`定义行为检查。**已核查资料、已写代码、测试通过、正式发布是不同状态。** 尚未登记证据的条目不能标为完成。

参考站主场景为前卫南区，北区属于本次扩展。南区纳入本次取得的整个校园范围与全部83个建筑面；北区纳入本次独立校界与26个建筑面，同时保留资料稀疏提示。“校界内数据全部导入”不等于“现实校园每处细节都已完整测绘”。

## 空间与渲染设计

当前实现使用原创Canvas2D，不依赖Phaser。世界保持米制坐标，`createTransform`统一203°展示变换；基础比例10像素／米，镜头缩放0.4–2。地表512×512像素块使用最多48块LRU缓存，建筑和树木采用空间索引剔除，人物脚部碰撞约0.65米。具体参数可按实测修订，不把技术栈相同视为视觉相同。

1. 保留WGS84原始几何与OSM标识，再投影到EPSG:32651。局部坐标为x向东、y向南，单位米。203°旋转与0.68纵向美术投影集中管理，屏幕点选同步使用逆变换。
2. 展示缩放与旋转由单一变换管理，建筑、地表、POI、人物、碰撞、小地图、传送共同使用。不可只旋转底图或重复旋转相机。
3. 建筑轮廓保留外环和孔洞。地面阻挡基于建筑底面、水域及真实障碍；树冠和屋顶负责遮挡，不直接等同地面碰撞。
4. 建筑按用途生成立面、门窗、屋顶和设备，重点地标采用独立特征。未测楼高只能作为渲染参数，不能当事实高度。
5. 对静态地表分块缓存，动态角色与环境按视口裁剪；远处纹理与对象回收。禁止一次生成覆盖整个校园的超大RGBA纹理。
6. 角色脚点为排序基准，使用小碰撞体；移动分步避免低帧率时穿墙。弹窗、输入框、窗口失焦时释放按键，移动端支持摇杆与交互。
7. 日新楼与中心图书馆的室内为独立区域，进出时切换遮顶、物件与天气显示；明确其艺术化布局属性。

天气与时间分别处理：日夜按北京时间计算；自动天气已实现Open-Meteo公开接口调用，约每10分钟请求长春坐标的当前温度、天气码、风速和昼夜字段。当前界面根据温度与天气码显示状态；请求失败显示“天气离线”并采用晴天环境，手动雨雪标注“模拟”。该项目前仅确认代码接入，部署网络访问、在线／离线切换与画面效果仍需实际验收。

全校地图共享同一份几何。当前以独立`navigation-worker.js`计算有界A*辅助路线，距离超过200米时使用4米网格，否则使用2米网格，最多18000节点；返回路径的每段再次复核碰撞，不连通时退回标记提示；它不是核实过门禁／实际通行条件的校园步行导航。搜索在后台执行，避免阻塞主画面。标记给方向和距离；传送必须寻找可站立位置并遵守冷却，服务端再次检查。若增加真实导航，需要从原始OSM节点建立拓扑，复核台阶、施工、门禁与入口连接，不能用直线代替路线。

## 联机架构与接口约定

当前部署保持既有站点身份与受众。普通Worker内存不是跨客户端共享房间的可靠真值；地图、消息和玩家状态不能依赖命中同一进程。D1中的独立 `campus_` 表保存校园模块数据，使用显式迁移，不在每次请求中执行DDL。

初期每组8人是测试目标，不是已验证容量。位置更新、心跳、快照读取频率需要同时考虑用户体验、请求量和D1负担；HTTP回退必须在界面显示，不能把它称为10Hz WebSocket实时同步。

接口以实现为准，当前约定如下，均需验收：

| 路由 | 作用 |
|---|---|
| `/api/campus/health` | 服务与存储状态 |
| `/api/campus/session` | 创建服务端匿名会话 |
| `/api/campus/me` | 读取／更新当前会话资料 |
| `/api/campus/rooms` | 列出校区房间与在线人数 |
| `/api/campus/join`、`leave` | 加入／离开指定房间 |
| `/api/campus/sync` | 输入序号、位置、心跳及快照的HTTP同步 |
| `/api/campus/teleport` | 校验白名单地标与安全落点后传送 |
| `/api/campus/snapshot` | 当前房间共享状态 |
| `/api/campus/messages` | 广场／房间消息、历史及本人删除等操作 |
| `/api/campus/ws` | WebSocket传输；平台透传能力待部署验证 |

会话token由服务器随机签发，数据库只存SHA-256摘要；HTTP用Bearer验证，WebSocket通过 `Sec-WebSocket-Protocol` 的 `campus-v1` 与 `campus-token.<token>` 传递，避免URL携带token。ChatGPT身份若存在，只由服务器做归属关联，不能信任客户端userId。昵称允许重复，身份由会话区分；匿名会话不等同手机号注册或实名认证，丢失凭据后的恢复能力必须明确。

服务端检查校区／房间归属、序号、有限速度、请求频率、地图边界、建筑孔洞与水域碰撞；传送只允许服务器校验的地标落点。聊天应以纯文本显示，防重复发送、越权删除和过快发送。默认广场按校区划分，同校区各组共享；可选房间频道仅当前房间可见。参考站只有南区，因此跨校区隔离属于本站新增规则。

WebSocket升级成功时，消息输入与D1共享状态使用同一业务规则。升级不可用时回到HTTP，仍返回真实快照，不制造假在线角色。自动重连必须清除失效状态、避免重复会话，超时玩家通过心跳TTL移除。扩容时迁往独立房间服务，而非无止境提高D1位置写入频率。

## 实施与验收关卡

- **分析关卡**：数据来源、参考行为、资源缺口、部署能力与明确差异记录完成后，再展开工程。
- **场景关卡**：南区全部83建筑可定位、北区已取得范围可切换；移动／碰撞／地图／传送／室内完整贯通。
- **联机关卡**：两个独立客户端同组互见、换组隔离、同校区广场跨组消息、断线恢复、历史持久化；八人压力与延迟待实测。
- **体验关卡**：相同地标视觉对照、手机操作、不同时间与环境、持续漫游性能，任何未通过项保留在计划。
- **发布关卡**：TypeScript检查、相关Node测试、实际浏览器检查与发布回执。源码、数据版本、测试证据共同保存，运行数据与凭据不进Git。

详见同目录《验收矩阵.md》和《迁移方案.md》。原站功能近似程度必须由实际结果判断，不能由计划长度或“已部署”推定。
