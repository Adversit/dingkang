# 前卫校园迁移方案

更新：2026-10-25。当前目标是先在既有站点运行，后续用户决定时再迁到自有云。本文件是可执行的迁移设计，**不代表已部署外部云或完成数据迁移**。

## 当前边界

- 前端：`public/apps/jlu-campus/`，独立校园资源与交互。
- 地图：`data/qianwei-south.json`、`qianwei-north.json`及来源、ODbL许可、质量记录；原始OSM快照和转换脚本在`docs/campus/map-source/`。
- 协议：`/api/campus/*`，会话、房间、同步、传送、消息与WebSocket。
- 数据：D1的`campus_`独立表，显式迁移；运行数据不提交源码。
- 身份：服务器随机签发匿名会话token，数据库只保存摘要。匿名凭据不等于永久可找回账号。

## 目标云架构

前端静态文件可放CDN／对象存储，FastAPI提供HTTP与WebSocket服务，PostgreSQL保存用户／房间元数据、聊天和管理记录。高频位置由权威房间进程管理，按需要快照；房间多实例时再引入Redis进行房间发现与消息转发。不要逐帧持久化每个玩家位置。

保持地图格式、公共地标派生规则和客户端接口语义，优先只替换联机适配层的服务地址。坐标系、时间戳单位、输入序号、房间校区、传送地标ID和消息幂等ID保持不变；变更必须新增协议版本，不能静默改变字段含义。

## 迁移步骤与验收

| 步骤 | 操作 | 验收与回滚 |
|---|---|---|
| 1. 固定版本 | 记录当前Git提交、地图版本、数据库迁移版本与协议版本 | 能还原当前部署源码；不导出明文凭据 |
| 2. 备份数据库 | 在受控位置导出campus表、结构和必要运行记录 | 逐表行数、主键、消息ID与时间范围校验；备份不进Git |
| 3. 建立云服务 | FastAPI实现同协议、HTTPS、WS、会话验证、输入限流和权威碰撞 | 复用现有相关测试，旧客户端可对接 |
| 4. 导入低频数据 | 迁移资料、房间定义、历史消息、举报／管理记录 | 行数、校区外键、所有权和消息幂等一致；拒绝破损行 |
| 5. 处理身份 | 可转移摘要时保持token算法一致；不可转移时明确要求建立新会话 | 不根据昵称合并账号；不能迁移则不冒充恢复成功 |
| 6. 双环境验证 | 用独立测试房间接入新服务 | 双客户端、换组、广场／房间聊天、删除／举报、断线重连、8人目标测试 |
| 7. 切换服务地址 | 短暂冻结写入或维护窗口内导最后增量，再切配置 | 用新消息和双客户端确认真实连接；失败恢复旧配置与原服务 |
| 8. 观察与归档 | 记录延迟、错误率、连接数、带宽及资源 | 达到稳定观察条件后再停旧服务；保留回滚版本与数据快照 |

## 一致性与权限要求

高频位置无需迁移完整历史，可迁移最后安全落点或重置到对应校区安全出生点。移交时清理过期在线记录，不让旧心跳变成永久幽灵玩家。房间ID、校区ID、消息ID不得与不同环境混用。

会话token不得放入URL、Git、日志或导出报告。用户ID和所有权只信任服务端；消息作者不能由前端指定。WS接入应明确认证协议与过期策略，HTTP保持同等权限。部署域名改变时检查CORS、Cookie／Bearer及浏览器存储边界，避免以“昵称一样”判断是同一个人。

地图与渲染资产可独立迁移，OSM的署名和ODbL下载入口随发布继续保留。新版重新下载地图时应重新转换并检查孔洞、入口、安全传送与碰撞，不能直接覆盖运行数据而跳过回归。

## 扩容顺序

先测单房8人的稳定性和延迟，再增加房间数量；达到单房瓶颈后按附近区域订阅，限制广播范围与状态频率。服务器负责权威状态，客户端负责插值。只有在有明确负载证据后才引入多进程房间路由、Redis或独立消息服务。

扩容后的目标需要新的测试记录：同时在线人数、每房人数、同步频率、延迟分布、断线恢复、消息一致性、CPU／内存／网络和持久化成本。不沿用参考站UI中的“200人满组”作为本站承诺。
